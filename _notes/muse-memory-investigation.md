I asked Muse what it remembers.

[Muse is Meta's personal AI agent](https://ai.meta.com/muse/). It can work across connected apps, use a browser, and continue tasks in the background. I already use Hermes with Hindsight for memory, so I wanted to see how Meta had put this part together.

I named my instance Zuck. A little on the nose, but I couldn't resist asking Zuck what he knows about me. It returned an export of its memory files. There were profiles, daily notes, indexes, and a directory called `dreams/`. Inside that directory was a running assessment of how it should behave toward me, including: "Don't scale up unprompted proactivity until he responds to it."

That was worth following up. What gets written during a conversation? What happens to it afterward? And which of these files does Muse actually read when I come back?

I asked it to trace those paths and run a small comparison. What follows is a reconstruction from the files it exported and its report on its own runtime, not independent access to Meta's implementation. The useful result was a concrete memory architecture I could compare with my own.

## Muse's memory architecture

`MEMORY.md` was the obvious place to start, but it wasn't the whole memory. Muse kept the evidence behind a memory separately from the version it wanted available in future conversations.

| File | What it holds and how it gets there |
|---|---|
| `IDENTITY.md` | The assistant’s identity for this instance: its chosen name, with fields for character, tone, and a signature emoji. Muse saved "Zuck" here when I named it. |
| `USER.md` | A small profile card: name, timezone, and standing context. Updated as the assistant learns confirmed details. |
| `MEMORY.md` | The compact collection of durable facts, preferences, and commitments. Muse describes conversational writes and a background reconciliation step that keeps this current. |
| `memory/personalization.md` | A reviewed profile for tailoring recommendations. In this investigation, Muse prepared a draft from connected data, then saved the corrected, approved version. |
| `memory/<date>.md` | Daily working notes and extracted claims. These include corrections, quotes, and source-message references, written during sessions or by background extraction. |
| `memory/people/INDEX.md` and `memory/groups/INDEX.md` | Relationship context organized from conversations by background maintenance. The indexes help select context about a person or group for later chats. |
| `memory/shopping/PROFILE.md` | Domain-specific preferences derived from the personalization profile, for recommendations without rereading the whole profile. |

`IDENTITY.md` was a nice detail: Zuck gets a profile too. It describes the assistant I'm talking to, while `USER.md` describes me. That is a different job from remembering what happened between us.

The split between `MEMORY.md` and the daily records is the one I care about more. A tidy summary is convenient, but when it gets something wrong, I want to see the conversation behind it. Here, the current belief and its supporting record are separate things I can inspect.

One correction in the export had this shape, with the personal details removed:

```yaml
kind: correction
claim: <claim ID>
quote: <the user's correction>
supersedes: <earlier inference>
sources: <source message ID>
```

I liked finding the `supersedes` note here. The export kept both the correction and a description of the inference it overturned, which gave me something concrete to follow through the other files.

The `memory/bank/` directory reorganized the material into views:

| File | Intended contents |
|---|---|
| `memory/bank/experience.md` | Distilled episodes: what happened and how it went. |
| `memory/bank/opinions.md` | Stable preferences and judgments, promoted from strong or repeated signals. |
| `memory/bank/reflections.md` | A cross-cutting index of notable claims, with source-file and line references. Despite the name, this is not the dreaming process. |
| `memory/bank/world.md` | Durable facts and circumstances, organized separately from preferences. |

The separation of `experience.md` and `opinions.md` caught my attention. Remembering that something happened is different from deciding it reflects a stable preference. A bad interaction with a tool, for example, doesn't necessarily mean I dislike that tool. I like having a place for the episode without immediately turning it into an opinion about me. The file split makes that distinction visible, though it doesn't tell me whether Muse always gets the promotion right.

`world.md` takes that separation a step further: circumstances have their own home, apart from preferences. Meanwhile, `reflections.md` was less philosophical than its name suggested. It was an index into the evidence. The corrected claim appeared there and in `world.md`, both pointing back to the same daily record. Useful for finding a claim from different directions, but still only one piece of evidence.

That's a design choice I'd borrow. I want a short current memory for convenience, but I don't want it to be the only surviving account of what I said.

## How Muse assembles context

Once I'd sorted out the files, I wanted to know how much of this Muse actually reads. Does every chat begin with the whole archive? Its reported design is more selective: start with a compact set of standing files, then fetch details when they're needed.

*Two routes into context: load the standing files, then search and read additional records when needed. This simplifies the design Muse described; it is not a literal execution trace.*

At conversation start, Muse reports loading `IDENTITY.md`, `USER.md`, the compact `MEMORY.md`, personalization and relationship indexes, alongside its other standing files. It also loads the current alignment synthesis, which I'll get to below. There are context-budget limits, so a file's presence on disk does not guarantee inclusion.

The daily logs don't all go into the prompt. `memory_search` returns relevant snippets with memory URIs and file-and-line references; `memory_get` reads further detail. `memory_explain` can trace an individual claim back to its quote, source message, status, and what it replaced.

I like this compromise. Muse can start with enough context to be useful without dragging every old conversation into the prompt. The part I'd want most in my own assistant is that second route: when I question a memory, it can go back to the source instead of defending whatever made it into the summary.

I couldn't trace every update as neatly. One export says the bank indexes come from daily records and personalization; the investigation report describes derivatives of reconciled memory. The source links are visible, but those accounts leave me unsure about the complete update order.

The `dreams/` directory was where the investigation became more interesting to me. Muse wasn't only summarizing what it had learned about the user. It was reviewing how its own interactions had gone.

A dreaming pass looks over recent conversation evidence, corrections, unresolved threads, and previous guidance. It produces two different things:

| File | What the background pass writes |
|---|---|
| `dreams/<date>.md` | A dated reflection: what happened, what remains unresolved, what the assistant thinks it got wrong, and what to do differently. |
| `dreams/alignment/derived/ALIGNMENT_SYNTHESIS.md` | The current synthesis carried into later conversations: how to respond, what to confirm, and where to be cautious. |

The dated dream lets me read what the assistant concluded at that point. The synthesis is what it's supposed to carry forward. This also cleared up the confusing `reflections.md` name for me: that file helps find claims; the dreaming pass interprets how interactions went and proposes what to do differently.

*The dated dream records a past review. The current synthesis carries its guidance into later conversations. These are the main jobs in Muse's reported process, not a literal call sequence.*

What interested me here was the review between an interaction and a lasting recommendation. **Observe** identifies corrections and unresolved friction; **Reflect** proposes guidance from them. **Grounding** checks whether the supporting evidence exists. **Consistency** checks whether the proposal contradicts prior guidance, while **preservation** guards against silently dropping something already established. Unresolved friction can open a repair thread.

Those are useful checks to have. They still don't make an inferred lesson the same thing as a preference I explicitly approved.

Here, "alignment" means changing the guidance supplied in later prompts, not updating the model's weights. That guidance can influence what Muse recommends; runtime approval gates still govern actions that require permission.

I went back to the correction to see what survived this process. Its wording was preserved in the daily record and indexed in the bank files. By the time I reached the dream and synthesis, it had become part of a broader lesson: confirm personal details before saving them. That lesson combined the corrections with my explicit review-before-save preference.

The unanswered suggestion was more debatable. Muse had taken that interaction as a reason not to increase unsolicited proactivity. I can see why an assistant would choose caution there, but I hadn't explicitly asked for that rule. Seeing it beside my stated preferences made me want to know how Muse keeps the two apart.

Its answer exposed a gap. Muse described structured state for boundaries, confidence, and the lifecycle of adaptations, but that state was unconfigured in my instance. The guidance in use lived in Markdown. I like the idea of the structured representation; I wouldn't credit it with managing these distinctions when the export showed it wasn't active.

Even the metadata needed a second look. A dated dream had `prompt_hoisted: false`, which could make it look as though none of this reached the model. That flag referred to the historical artifact. The current synthesis had its own route into the prompt.

I also tried to pin down when this happens. Muse called it nightly and reported successful background runs, but I couldn't find the exact trigger in the visible cron inventory. I wouldn't infer a scheduler from a folder named `dreams/`. What I could follow was the separation between recording an interaction and coming back later to reconsider it. That second pass is the part I find compelling.

## Testing whether the synthesis changes the recommendation

After seeing the synthesis, I wanted to see whether it made a difference to an answer. As part of an eight-question investigation, I had Muse run an exploratory A/B-style comparison using two subagents.

The task was narrow. An earlier event suggestion had gone unanswered. Should the assistant recommend sending one follow-up?

One subagent used the full context, including the synthesis. The other was instructed to disregard the synthesis and use `MEMORY.md`, daily logs, and the personalization profile.

| Source-use instruction | Returned recommendation | Rationale it cited |
|---|---|---|
| Include the synthesis | Don't follow up | The synthesis said not to increase unsolicited proactivity after the unanswered suggestion. |
| Disregard the synthesis | Send one light follow-up | The topic matched a remembered interest, and there was no explicit refusal. |

That contrast got my attention. The profile supported an event suggestion; the synthesis supported leaving it alone. I could see why the extra layer might matter, even though this was only one scenario with two responses.

Then I found a bug in the experiment design: the supposed control still had access to the synthesis. Muse's subagents inherit the transcript, so the second agent had only been *told to ignore* it. That's not the same as removing it. This is a flaw in the comparison, not evidence of a bug in Muse's memory system.

The source-use reports were also self-reported, and there were no repetitions. I can't attribute the difference to the synthesis alone or call either answer better. What I can say is that the two rationales match the different jobs these files are meant to do.

That left me interested in the mechanism, even without a clean A/B result. A preference can tell Muse what I might like. The synthesis can give it a reason to hold back on acting on that preference.

## How this compares with my Hermes + Hindsight setup

[My current setup](https://praveenks.com/notes/from-honcho-to-hindsight/) uses Hermes as the assistant and Hindsight as its memory backend. The fair comparison is that combined system against Muse, not Hindsight alone against an entire personal agent.

Looking at my own stack, I didn't come away thinking I needed to rebuild everything. Hermes retains and recalls conversational memory automatically, alongside its standing memory and user-profile files. Hindsight [consolidates observations](https://hindsight.vectorize.io/developer/observations) and supports [derived mental models](https://hindsight.vectorize.io/developer/api/mental-models). It keeps supporting sources, invalidates dependent observations after explicit edits or deletions, and schedules eligible derived-memory refreshes.

What I liked about Muse was being able to open named files and follow the work between them. Mapping those jobs onto my setup made the overlap clearer:

| Part of the memory system | Muse, as described in the exports | My Hermes + Hindsight integration |
|---|---|---|
| Starting context | Memory, profiles, indexes, current synthesis | Standing files + automatic recall |
| Deeper memory | Daily records + claim retrieval | Memories, observations, historical archives |
| Derived understanding | Dated dream + current synthesis | Consolidation + mental models |
| Updating old beliefs | Source-linked corrections; views refreshed separately | Backend invalidation and refresh; other context surfaces handled separately |

The integration boundary is where I see work worth doing. In the Hermes provider I inspected, recall returns memory text and reflect returns a synthesized answer. Those responses don't carry the full structured evidence record into the prompt. My archive adapter already labels historical inferences as untrusted evidence and says current user statements take precedence, but that doesn't coordinate every copy of a memory.

Muse isn't a finished solution to that problem either. Its forgetting specification says historical dreams remain, and the current synthesis is re-derived on a later background run rather than synchronously rewritten. I read that specification; I didn't exercise deletion to verify propagation in practice.

The comparison doesn't persuade me to replace my memory backend. It gives me a better idea of what I want the pieces around it to do.

## Three changes I want in my own memory stack

### Make a correction stick across sessions

Muse's correction trail is useful because I can follow it beyond the original record, into indexes and later reflection. I'd like the same visibility across my whole setup. Hindsight already handles backend invalidation and eligible refresh; the missing piece is coordinating that with Hermes's standing files, recalled material already in a conversation, and historical archives.

If I correct a claim, the current chat and a fresh session should both stop treating the old version as current. An archive returning it shouldn't quietly undo the correction. That's the behavior I want to test, rather than stopping at a successful database update.

### Keep guesses distinguishable from requests

Muse's synthesis mixed an explicit review-before-save preference with an inferred response to an unanswered suggestion. Both can be useful, but I'd want Hermes to retain the distinction when it recalls them: what I asked for, what it inferred, where that inference applies, and whether I later confirmed or rejected it.

Hindsight's sourced records provide a foundation. My integration needs to carry that information into the context the assistant actually receives, rather than flattening everything into equally authoritative prose. A useful adaptation can stay tentative until I give it more support.

### Don't count the assistant repeating itself as new evidence

One corrected claim appeared in a daily record, bank views, a dream, and the synthesis. That duplication helped me navigate the system. It didn't create more evidence.

I'd preserve that ancestry through recall and retention in Hermes. Suppose an assistant infers that a project favors small patches, recalls that inference next week, and repeats it in its answer. Saving the answer should not turn the same inference into a second user confirmation. Hermes already retains user and assistant roles with session lineage, and Hindsight keeps supporting sources. I want those foundations to distinguish new evidence from a recycled conclusion throughout the round trip. This is a property to establish, not a double-counting failure I've demonstrated in Hindsight.

I went into this looking for how Muse stores memory. The part I'd borrow is the inspectable path around storage: the source record, the current view, the reflection, and what arrives in the next conversation. I can keep my existing backend and still make those connections much easier to follow.
